The shared layer

Architecture that keeps connectors consistent

The Core owns the reusable integration model. A connector contributes the external API client and platform-specific workflows, while administrators work with one familiar configuration and monitoring experience.

External platform→Provider connector→eCommerce Core→OCA queue_job→Odoo records

Backend

External system, company scope, credentials, provider capabilities, and a dedicated queue user.

Store

Website, store view, warehouse, stock location, currency, automation, batch sizes, and scheduling for one sales channel.

Mappings

Persistent links for products, variants, attributes, categories, customers, orders, invoices, payments, shipments, refunds, carriers, payment methods, and inventory sources.

Sync state

Per-store and per-resource cursors, last success, last failure, and incremental replay controls.

Queue orchestration

Bounded coordinator and child jobs with channels, retry policies, deduplication keys, and progress runs.

Observability

Events, actionable issues, mapping status, and queue state make failures visible instead of hiding them in logs.

Important: this module does not connect to an external platform by itself. It is the shared foundation and dependency for a provider connector such as Magento Connector for Odoo.

Configuration

Configure once. Operate from one place.

02

Backends and Stores

Separate external systems from the sales channels inside them. A Backend holds credentials and provider capability; a Store holds the website, store view, warehouse, stock location, currency, and automation settings.

  • Company-scoped configuration and record rules
  • Manager-only credential access
  • Per-Store queue scheduling and batch sizes
  • Test Connection and Preflight from the form
03

Store synchronization

Run supported catalog, order, inventory, shipment, and finance operations from a Store. Jobs are queued through OCA queue_job and report state back to the Store.

  • Import, Export, and Update operations where supported
  • Bounded batches and deduplicated queue identities
  • Safe replay through existing mappings
  • Visible progress and structured issues

Queue & reliability

Background work designed for real operations

04

OCA queue_job with a dedicated integration user

Slow API calls do not block the web client. Coordinator jobs split long work into bounded child jobs, and deterministic identity keys prevent accidental duplicate enqueueing of the same unit of work.

  • Separate channels for catalog, orders, inventory, shipments, and finance
  • Retry policies for transient external failures
  • Company-scoped job execution
  • Failed jobs and synchronization issues stay inspectable
Refunds

Credit Notes with an explicit export boundary

Posted customer credit notes can be sent to a selected Store through the provider-neutral refund wizard. The core validates the Store and mapping context, queues the operation, and only marks the credit note as refunded after the provider confirms success.

Provider-neutral wizard

Select a company-scoped Store; the connector supplies its own return method and confirmation rules.

Safe failure state

A queued or failed refund never sets the refunded flag. Pending or uncertain attempts are reconciled before retry.

Duplicate prevention

Credit-note identity, existing mappings, and provider evidence prevent a second refund for the same document.

Installation

Install the Core in six steps

  1. Install the OCA queue_job 17.0 branch. Add the repository root to addons_path.
  2. Install queue_job from Apps.
  3. Place odoo_ecommerce_integration in your addons path and update the Apps list.
  4. Install eCommerce Integration Core.
  5. Enable the queue runner: workers = 2 and server_wide_modules = web,queue_job, then restart Odoo.
  6. Install a compatible connector such as Magento Connector for Odoo. The Core alone does not contact an external platform.
